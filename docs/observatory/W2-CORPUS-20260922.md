**Corpus: 2026-09-22, PCP, Grok runtime, `duration >= 30`, canonical SIDs.**

## THE HEADLINE — it is not the gate, there is no filer

The spec (`SPEC-20260923.md` §4, W2) said to find the specific reason
`sweepPcpUnfiledCall` turned these calls away. **It did not turn them away. It
has never run on this lane, and there is no other teardown filer behind it.**

**1. `sweepPcpUnfiledCall` is wired into the OLD CORE only.** Its single
caller is `src/voiceAgentRoutes.ts:4713`, inside the OpenAI SIP session's
`finally` block (`[SESSION] Call <id> ended, cleaning up...`). A Grok runtime
call never enters that function — the runtime tears down in
`src/runtime/voiceRuntime.ts`. **PCP moved to the runtime 2026-09-04.**
`markPcpCallEnded` (`voiceAgentRoutes.ts:4663`) is in the same block and is
equally unreachable.

**2. The runtime's own teardown sweep excludes `pcp` by table.**
`voiceRuntime.ts:1219` calls `runRequestSweep` -> `decideSweep`, whose FIRST
line is `DEPARTMENT_BY_SLUG[input.slug]`:

```
optical: 1, surgery: 2, tech: 3, records: 16     // requestSweep.ts:54
```

`pcp` is absent, so every PCP call exits at `reason: "not-a-queue-lane"`
before any other test. So on the runtime PCP has **no teardown filer at all**:
the lane-specific floor is not wired, and the generic sweep declines the lane.

**3. Positive confirmation from production, all time.** The sweep is the only
writer of `failureInformation` = `caller_hung_up_before_completion` or
`call_not_classified` (`pcpAgent.ts:2901`). Across ALL of
`voice_agent_api_logs`, **0 POSTs have ever carried either value** — so the
v18/v30/v31 floor has never filed a single ticket on either pipeline.

## A CORRECTION TO THE SPEC

`SPEC-20260923.md` §4 read the day's **133 accepted `unclassified_call`
POSTs** as evidence that the slug path works and therefore that the gate, not
the wiring, was the problem. The slug IS accepted — that half is right — but

## WOULD WIRING THE SWEEP RESCUE THEM? PARTLY, AND ONE GROUP IS PROVEN NOT TO BE

The gate's three admissions (`pcpAgent.ts:2665`):

1. `toldUsSomething` = `callPurpose` AND one of (`callerName`,
   `patientFirstName`, `patientLastName`, `statedRelationship`)
2. `askedForAPersonAndDidNotGetOne` = `callPurpose` AND `callerRequestedHuman`
3. `unclassified` = **`!callPurpose`** AND `saidMoreThanTheirOwnIdentity`

Reconstructed PHI-free from each call's LAST `record_pcp_intake` outcome
(`nextField`, `disposition` — field names only, allow-listed in
`toolTimeline`):

- **All 38 had a `callPurpose` set** (`disposition` present on every one).
  So **admission 3 — the v31 `unclassified` arm, built for exactly this
  population on 09-15 — cannot fire on any of these 38.** It requires the
  purpose to be ABSENT.
- **11 calls have `nextField: 'callerName'`**, i.e. the name was still the next
  ask, so it was unset; the patient fields come after it in
  `PROFESSIONAL_FIELDS` and `statedRelationship` is no longer asked at all
  (v33). So `toldUsSomething` is FALSE. **Those 11 fall through all three
  admissions and would NOT be rescued by wiring the sweep as written.**
- **11 calls ran `record_automated_resolution`**, which POSTs `AUTOMATE` and
  records a disposition; the app answers 200 and deliberately creates no
  ticket. Those are the designed no-ticket path and are correctly ticketless —
  and they are why the 09-08 taxonomy's filing-tool predicate understates
  filings on this lane: **`record_automated_resolution` is a filing path that
  predicate does not name.**
- **The remaining 16 are NOT determinable from the timeline**, and the reason
  is worth recording: `nextField: null` does NOT mean the intake was complete.
  `missing` is drawn from `askableNow`, which excludes fields whose ask budget
  is spent (v33) and the `ENRICHMENT_AFTER_FILING` fields held back before a
  disposition (v37). So null means "nothing we are willing to ask", and a
  field can be unset and unaskable at once. An earlier draft of this file read
  those 16 as "form complete, `toldUsSomething` true" and published a
  16/11/11 split on it; that inference is withdrawn. **Their transcripts
  settle it and that is the next step.**

## WHAT ELSE FALLS OUT — the sweep's `finally` is the only thing that frees per-call state

`pcpDirector.clear(callId)` has exactly two callers: `terminate_call`'s
success branch (`pcpAgent.ts:1990`) and the sweep's `finally` (`:2912`).
`pcpCallMetadata.delete` has one: the sweep (`:2667`).

On the runtime **neither fires**:

- the sweep never runs (findings 1 and 2), and
- **94 of 94 `terminate_call` events on 2026-09-22 returned `success: false`**
  — 92 at HTTP 400, 1 at 504, 1 with no status — because that tool POSTs to
  OpenAI's SIP hangup endpoint, which is the old core's. CLAUDE.md's v56 row
  already records this as 404s on 09-16 and harmless; the status has changed
  and the consequence has not. `response.ok` false means
  `pcpDirector.clear` is skipped.

`PcpDirector.states` and `pcpCallMetadata` are both uncapped `Map`s, and the
metadata holds a **transcript getter per call**. So every PCP call the process
ever serves leaks its director state and keeps its whole transcript reachable
for the life of the process. That is a memory leak AND PHI retained in memory
indefinitely. Not a caller-facing defect; it is the same root cause and should
be fixed with it.

# THE 16 UNDETERMINED CALLS ARE RESOLVED — 2026-09-23, and no transcript was needed

The section above left 16 of the 38 unclassifiable because `nextField: null`
is ambiguous. **`askBudgetSpent` removes the ambiguity**, and it is on the
same intake outcome, PHI-free, field names only: it lists exactly the fields
we STOPPED asking for, which is the only reason a `nextField` can advance
past an unset field. Two facts make it decisive:

- `missing = askableNow.find(...)` returns the **first** unset askable field
  in the required order, and `PROFESSIONAL_FIELDS` is purpose -> `callerName`
  -> `callerOrganization`, then the patient, then
  `PROFESSIONAL_ENRICHMENT` (`callerRole`, `callerEmail`, callback).
- A field can only be skipped by being **answered** or by being **unaskable**,
  and unaskable means either its ask budget is spent (it then appears in
  `askBudgetSpent`) or it is an `ENRICHMENT_AFTER_FILING` field, which
  `callerName` is not.

So **a `nextField` past `callerName`, with `callerName` absent from
`askBudgetSpent`, means `callerName` was answered** — and `toldUsSomething`
is therefore true.

## A CORRECTION TO THIS FILE'S OWN EARLIER CLAIM

The section above says "**All 38 had a `callPurpose` set**", derived from
`disposition` being present on the LAST intake event. `CA15e6dd4d6c` shows
the limit of that: its `handoff_to_pcp` refused for a MISSING purpose, so the
purpose was absent earlier in the call and recorded later. The claim is true
**at teardown**, which is when the sweep reads it and is all the sweep
conclusion needs — but it is not true throughout the call, and an earlier
tool refusal is not evidence about the end state. Stated because the next
reader will otherwise use that sentence to rule out a mid-call purpose gap.
