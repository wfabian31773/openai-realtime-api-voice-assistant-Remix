### 1.3 The one remaining fork — and the instrument cannot see it

`rememberVerifiedIdentity` returns early, **silently**, on three conditions:

```ts
if (!isTwilioCallSid(callSid) || !firstName || !lastName) return;
```

All three leave the map empty. So `storeSize 0` / `no_entry` means
*"nothing was ever stored"* and says nothing about **why**: a refusal and a
call that never happened are byte-identical in the telemetry.

**CORRECTION TO v58's OWN DESIGN NOTE — someone will rely on it.**
`verifiedIdentity.ts` and the CLAUDE.md v56 row both say a write/read SID
disagreement shows up as `storeSize > 0 && hasEntry false` (the `key_mismatch`
arm). **That is false for the case that matters.** A non-canonical write SID is
refused at the guard, nothing is stored, and the map stays empty — so the
`key_mismatch` arm can only fire when the write SID is canonical *and
different*, and §1.2 now says it is neither. The arm was built to test a
hypothesis it structurally cannot reach.

**Reading the code says the write must fire.** Every link was checked:
`certain: true` ⇒ `uniqueMatch: true` ⇒ the `if (uniqueMatch)` block, and
`identity_is_certain` is reported from exactly one site, below it, in the same
function. `runTool` hands `def.handler` the **full** input — `validateInput`
only checks `required` and strips nothing. The adapter's injected canonical
`call_sid` beats the model's guess (`{ ...supplied, ...injected }`), and
`lookup_patient` not declaring `call_sid` in its schema does not matter,
because injection happens after SDK validation.
`patientData.firstName/lastName` come off the raw row — `buildContext` takes
`rows: any[]`, so `firstApt` is the drizzle-mapped Schedule row and
`PatientFirstName` / `PatientLastName` are real columns.

**Production says the map is empty. One of those premises is wrong and no
amount of reading settles which.** That is the honest state.
